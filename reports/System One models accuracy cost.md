# Test cheap decision models before training anything

The cheapest experiments with the most information come first: run several off-the-shelf "decision models" on all 319 ASIMOV-2.0 text items. A decision model (also called a System One model) reads the scenario once and returns a probability for each answer option instead of writing text. The runs to start with are hosted Jev, OpenAI Decisions `gpt-6-luna`, the Codiv lineup (OpenJev, JevK5, Laya, Verdict) and a local Qwen-class 4B "option-logit" scorer. Then use the saved probabilities to simulate cascades, where the cheap model answers and hands only its unsure items to a big LLM. Each full hosted pass costs cents or nothing. Codiv's free tier alone covers the whole benchmark many times over ([Codiv](https://codiv.ai); [TypeSafe Models](https://docs.typesafe.ai/models)). The catch is that **nobody has published any of these models on physical-safety, injury or counterfactual questions**, and vendors' own docs list the exact weaknesses ASIMOV probes: multi-hop reasoning, ordinal (ordered) severity scales and a pull toward the first option ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)). Whether they beat general LLMs on accuracy per dollar is therefore an open empirical question, and the 319 items would be new evidence. The design choices that matter most are how to split the four questions, how to word and order the options, and how to measure cost fairly. Safety classifiers (Llama Guard, ShieldGemma, Granite Guardian) fit the task poorly because each one answers a single yes/no question. Fine-tuning a small model is possible within five days, but only on synthetic data built from NEISS injury reports from years other than 2023. No legitimate labelled training split exists.

Everything below is a set of options with evidence and costs. Which hypotheses to state, which runs to do and what the results mean are for the owners to decide (course rule). Every vendor number is the vendor's or author's own claim and has not been reproduced.

## Five ways to get "a probability per option," and which suit ASIMOV

The candidate systems differ in *how* they turn a model into option probabilities, and that mechanism predicts both their cost and their failure modes. The first family is **trained decision heads**: a small extra network on top of a language model, trained to score each option. Kev (0.8B/4B/9B) puts a LoRA adapter (a small set of trainable weights added to a frozen model) and a "pointer head" on a Qwen3.5 base. The head compares each option's internal representation with the question's, then takes a softmax, the function that turns scores into probabilities that sum to 1 ([Kev README](https://github.com/jaredpalmer/kev)). Laya does the same with a 421M-parameter ModernBERT encoder that scores each option at a mask token ([Laya card](https://huggingface.co/convaiinnovations/laya)). The second family is **label-token readout**: an ordinary, frozen language model reads the prompt once, and you take the probabilities it assigns to the option labels as its next token. SemIf does this with a frozen Qwen3.5-4B ([SemIf README](https://github.com/TheoLeeCJ/SemIf)). OpenJev does it with a 26B diffusion model (4B active) and re-reads uncertain answers three times, averaging the results ([OpenJev README](https://github.com/razorback16/openjev)). The third family is **NLI zero-shot**. A model trained on natural-language inference ("does sentence A imply sentence B?") scores "this scenario implies option X" for each option, then normalises the scores across options. That costs one forward pass per option, and DeBERTa-v3-large has a 512-token limit ([HF pipeline docs](https://huggingface.co/docs/transformers/main/en/main_classes/pipelines#transformers.ZeroShotClassificationPipeline); [deberta-v3-large-zeroshot-v2.0](https://huggingface.co/MoritzLaurer/deberta-v3-large-zeroshot-v2.0)). The fourth family is **closed hosted services**. Jev and OpenAI's `gpt-6-luna` return probabilities, but their documentation does not say how they compute them ([TypeSafe docs](https://docs.typesafe.ai); [OpenAI Decisions guide](https://developers.openai.com/api/docs/guides/decisions)). The fifth family is **safety classifiers**. Each returns P(unsafe) or P("Yes") for one policy. ShieldGemma, for example, takes a softmax over "Yes"/"No" and warns that it is "highly sensitive to how the safety principle is worded" ([ShieldGemma card](https://huggingface.co/google/shieldgemma-2b)).

The first four families take the 4 or 5 ASIMOV options directly as runtime inputs, with no training and no JSON to parse. Safety classifiers do not. To answer a 4-level severity question with one, you would write one policy per option, make 4-5 calls, and renormalise yes-probabilities that were never trained to be compared with each other. Granite Guardian's `custom_criteria` and ShieldGemma's free-text policies make this technically possible ([Granite Guardian 3.3 card](https://huggingface.co/ibm-granite/granite-guardian-3.3-8b)). Their published scores, though, are content-moderation scores: an F1 of about 0.83 on ShieldGemma's prompt set and a harm F1 of 0.81 for Granite. Neither measures injury severity. For H2, the most natural fit is Q3 collapsed to a yes/no question ("does the instruction raise injury risk?"). The worst fit is a 4-way severity question. Whether a collapsed Q3 still counts as "the benchmark" is a scoring decision for the owner.

## Published accuracy flatters these models on easier tasks

The published accuracy numbers come from routing and triage data, and most were measured by the authors themselves. On Kev's held-out "new sources" test, the author reports **Kev-0.8B 0.697, Kev-4B 0.838, Kev-9B 0.852, Kev-27B 0.889**, and Jev 0.857 on the dev set ([Kev README](https://github.com/jaredpalmer/kev)). SemIf-4B agreed with Jev's published answers on 0.845 of a 102-row subset, but scored only 0.637 on WANLI, a hard natural-language-inference set ([SemIf README](https://github.com/TheoLeeCJ/SemIf)). The sharpest warning comes from Laya's own card. **The base Laya checkpoint scored 0.362, below the 0.461 you would get by always guessing the most common answer.** It reached 0.766 only after fine-tuning on that benchmark's own training split. Ordinal "score" questions were its weakest type, at 0.372 on SST-5 ([Laya card](https://huggingface.co/convaiinnovations/laya)). TypeSafe publishes no accuracy, calibration or latency figures for Jev at all. OpenAI publishes none for `gpt-6-luna` beyond the speed claim.

Vendor guidance describes where these models should struggle, and it lines up with ASIMOV's questions. TypeSafe says each question should be "a quick gut-check judgment". If a question needs extended reasoning or weighs several factors, it advises splitting it up and combining the parts in code ([TypeSafe docs](https://docs.typesafe.ai)). Jev's list of known weaknesses includes multi-hop reasoning, "context rot" from irrelevant text in the input, score levels that are "weakly calibrated numerically", and **a lean toward the first option** ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)). Kev's README says it is weaker on knowledge-heavy questions and that changing option order can change answers ([Kev README](https://github.com/jaredpalmer/kev)). Mapped onto ASIMOV, Q1 (injury type, 5 named options) looks most like the "gut-check" tasks these models were built for. Q2 and Q4 are ordinal severity scales. Q3 and Q4 are counterfactual: they ask what happens *after* the robot's instruction. These mappings are expectations drawn from the docs, not measured results. Per-question accuracy for each system is the measurement that would test them.

Input length is a practical trap. The paper's full text prompt is about 1.3k tokens. Laya's English model reads 512 tokens and its options share 256 tokens, and both Laya and Verdict cut long input **silently** ([OpenJev README](https://github.com/razorback16/openjev)). Kev (validated to 8k tokens), JevK5 and Clef (16k) and Jev (32k) fit the full prompt. Any Laya or Verdict run therefore needs a short input (scenario plus instruction only) or a truncation check. Otherwise its accuracy reflects missing text rather than the model's judgment.

## Question design decides much of the outcome before any model runs

### Q2–Q4 cannot see Q1's answer unless you build that yourself

ASIMOV's Q2–Q4 refer to "the injury you identified in Q1". Jev evaluates every question "in parallel and in isolation against the same state", and Kev's isolation is exact: each question runs as its own row ([TypeSafe docs](https://docs.typesafe.ai); [Kev README](https://github.com/jaredpalmer/kev)). OpenJev's `sequential` flag conditions one *chunk* of about 12 questions on the earlier chunks. Four questions fit inside one chunk, so the flag probably does not let Q2 see Q1, though that is not confirmed ([OpenJev README](https://github.com/razorback16/openjev)). Three designs follow, each a candidate comparison. **Independent:** one call, with Q2–Q4 reworded to stand alone ("severity of the most likely injury"). It is the cheapest, but Q2 may silently pick a different injury than Q1. **Two-stage chain:** call 1 asks Q1, and call 2 asks Q2–Q4 with "Most likely injury: X" added to the input. It costs two calls, and a wrong Q1 answer drags Q2–Q4 down with it. Work on chained annotation reports gains but also this error path ([arXiv 2409.09615](https://arxiv.org/html/2409.09615v1)). **Weighted chain:** run call 2 once per Q1 option and weight the results by Q1's probabilities. This is our own idea, not from any source, and it costs about 5x for stage two. Comparing these designs on the 319 items measures how much the dependency matters. Q3 depends mainly on the instruction text, so it is likely the question least affected. Before choosing, check how the answer key scores Q2–Q4 when a model names a different injury than the key. That is an open scoring definition, so stop and ask the owner rather than pick one.

### Short questions, rubric moved into option descriptions

TypeSafe advises starting with "a one-line description per option". It suggests adding structure only when the model keeps confusing two options, and it notes that option names *and* descriptions are both sent to the model ([TypeSafe Choice](https://docs.typesafe.ai/primitives/choice)). For ASIMOV, a natural variant moves the severity rubric into each option's description ("Moderate: needs medical treatment, not life-threatening…") and keeps the question text short. Wording effects are large. Sclar et al. found meaning-preserving format changes moved accuracy by **up to 76 points**, and this sensitivity did not disappear with scale or instruction tuning, so they recommend reporting a range across formats ([arXiv 2310.11324](https://arxiv.org/abs/2310.11324)). Running 2–3 wordings and reporting the spread is better evidence than any single wording. The paper's prompt stays verbatim for the reproduction runs, and every variant goes under `experiments/` with its own run name.

### Semantic option names beat letters on bias

Much of the bias in multiple-choice scoring comes from the letters themselves: models carry a prior preference for "A" or "C". PriDe showed that removing option letters cut that bias sharply. For gpt-3.5-turbo, the spread of accuracy across answer positions fell from 5.5 to 1.0 on MMLU. The same change cost 2–7 accuracy points on average ([PriDe, arXiv 2309.03882](https://arxiv.org/html/2309.03882)). OpenJev already letters options internally ([OpenJev README](https://github.com/razorback16/openjev)). Sending our own "A"–"E" as option names therefore shows the model a letter twice. Kev scores option *content* positions rather than letter tokens ([Kev README](https://github.com/jaredpalmer/kev)). The repo currently plans letter names for Decisions and Jev. A run with semantic names (`no_injury`, `minor`, `moderate`, `severe`) is a cheap variant that tests whether letter priors matter here. Keep Q1's "No realistic injury possible" with a clear description: TypeSafe recommends a "none" option, while Kadavath et al. found models are biased *against* choosing "none of the above" ([Kadavath et al. 2022](https://ar5iv.labs.arxiv.org/html/2207.05221)).

### Option order is a measurable, cheaply removable bias

Reordering options shifts LLM accuracy by roughly **13% to 75%** across benchmarks ([Pezeshkpour & Hruschka, arXiv 2308.11483](https://arxiv.org/abs/2308.11483)). Cyclic permutation runs each question once per rotation of the options, so every option appears in every position. It costs n passes (5x for Q1, 4x for Q2–Q4) and gained **+4.9 to +7.9 accuracy points** zero-shot. PriDe estimates the model's position preference from 5% of items, without labels, at 1.15–1.2x cost ([PriDe](https://arxiv.org/html/2309.03882)). Size and instruction tuning do not reliably remove the bias. Jev leans toward the first option, and Kev offers a `/permute` endpoint, but its README does not document how orders are chosen or how results are combined ([Kev README](https://github.com/jaredpalmer/kev)). At hosted decision-model prices a 5x run still costs cents, so the real cost to report is extra latency and tokens. For Q2–Q4, whose options have a natural order, a cyclic shift wraps that order around and a full reversal is a cheap second check. Reporting the size of the bias (accuracy and answer distribution under two or more orders) is more informative than always debiasing.

### Choice versus score for the severity questions

Decision APIs offer a `score` question type: ordered levels, returning the expected level Σ i·pᵢ plus the full distribution ([OpenJev README](https://github.com/razorback16/openjev); [OpenAI Decisions guide](https://developers.openai.com/api/docs/guides/decisions)). Laya's and Jev's docs flag score questions as weak, so asking Q2 and Q4 as `choice` versus `score` is itself a variant to run. For extra signal beyond the paper's accuracy, the probability-weighted level follows G-Eval's approach. In G-Eval it lifted correlation with human scores only slightly, 0.514 vs 0.502 ([arXiv 2303.16634](https://arxiv.org/html/2303.16634)). Mean absolute error on the severity level would separate "Moderate vs Severe" slips from "None vs Severe" errors. Adding any such metric is a scoring decision to log in WORKLOG.

## Reading logits from a small chat model is cheap but can disagree with its own answer

For a local small LLM such as Qwen3-4B, the cheapest approach is to read the probability of each option letter as the next token, with no generation. The risk is documented. Wang et al. found first-token probabilities and the model's written answer **disagree more than 60% of the time** for some chat models. Models "heavily fine-tuned on conversational or safety data" were worst, and the gap persisted even with tightly constrained prompts ([arXiv 2402.14499](https://arxiv.org/abs/2402.14499)). When the two disagree, the written answer holds up better when the question is reworded or the options reordered, even against PriDe-debiased probabilities ([arXiv 2404.08382](https://arxiv.org/abs/2404.08382)). Safety tuning is exactly the trait at stake in a physical-danger benchmark, so a cheap check is to generate the text answer for a `--limit` sample and report how often it agrees with the logit answer. Robinson et al. show that letter scoring depends on the model's "symbol binding" ability (linking a letter to its option), which "varies greatly by model" ([arXiv 2210.12353](https://arxiv.org/abs/2210.12353)). Scoring each option's text likelihood instead avoids letter priors but costs accuracy on average (PriDe). Two more notes. Logit scoring cannot refuse, so the repo's `refusal_rate` should be recorded as "not applicable" rather than 0. And SemIf's reranker mode, which scores each option as a separate query-document pair, did worse than direct option logits (0.560 vs 0.845 on its TypeSafe subset) ([SemIf README](https://github.com/TheoLeeCJ/SemIf)).

## Calibration, cascades and cost need careful measurement at n = 319

**Calibration** means a model's stated confidence matches how often it is right: answers given at 80% confidence should be correct about 80% of the time. The usual summary, ECE (expected calibration error, the average gap between confidence and accuracy over confidence bins), is biased and noisy on small sets, and most biased for models that are nearly calibrated ([Roelofs et al., AISTATS 2022](https://arxiv.org/abs/2012.08668v3)). On 319 items, the more stable primary numbers are the Brier score (mean squared error of the probabilities) or log-loss, both computed over all options. ECE works as a secondary number with about 10 equal-mass bins (bins holding equal numbers of items), a reliability diagram, and bootstrap confidence intervals that resample whole items rather than individual questions, because an item's four answers are correlated. Kumar et al.'s `uncertainty-calibration` package computes these with intervals ([Verified Uncertainty Calibration](https://papers.nips.cc/paper/8635-verified-uncertainty-calibration); [code](https://github.com/p-lambda/verified_calibration)). Not every system offers the same signal. Decision models give full distributions; generated LLM answers give at most a letter logprob or a stated confidence. Stated ("verbalized") confidence is often better calibrated than token probabilities for chat models ([Tian et al. 2023](https://arxiv.org/abs/2305.14975)), but it still tends to be overconfident ([Xiong et al., ICLR 2024](https://arxiv.org/abs/2306.13063)). Each calibration number should say which systems it covers.

Temperature scaling divides a model's scores by one fitted number to soften or sharpen its probabilities. It **cannot change accuracy**, because the top answer stays the same ([Guo et al. 2017](https://ar5iv.labs.arxiv.org/html/1706.04599)). Fitting it, however, requires labelled data. Every vendor advises calibrating on your own data, and we have no labelled data except the 319 eval items. One workaround is 5-fold cross-fitting: fit the temperature on four folds of items and apply it to the fifth, so no item's own label is used to fit its score. This still uses eval labels, which arguably breaks the "never tune on eval items" rule, so the owner must decide before anyone runs it. The clean alternative is to fit on external or synthetic data.

A **cascade** lets a cheap model answer and sends only its low-confidence items to an expensive model. Published savings are large: FrugalGPT reports matching GPT-4 at "up to 98%" lower cost ([arXiv 2305.05176](https://arxiv.org/abs/2305.05176)), AutoMix over 50% ([arXiv 2310.12963](https://arxiv.org/abs/2310.12963)) and RouteLLM over 2x ([arXiv 2406.18665](https://arxiv.org/abs/2406.18665)). Those results come from settings where the small model is usually right, not from a hard safety set. The useful fact for this project is that **a cascade can be simulated for free**. Given cached decision-model probabilities and cached LLM answers for all 319 items, sweep the confidence threshold from 0 to 1, take the small model's answer above the threshold and the LLM's below it, and plot accuracy against cost. Three details keep this honest. First, defer whole items, since one LLM call answers all four questions. Second, show the whole curve rather than one tuned threshold; if a single point is needed, choose the threshold on held-out folds. Third, add an "oracle router" upper bound that defers exactly the items the small model gets wrong. Temperature scaling does not change this curve. Only how well confidence *ranks* right versus wrong answers matters ([Gupta et al., arXiv 2404.10136](https://arxiv.org/abs/2404.10136)). Results must come from a script reading `results/`, not a notebook, per the repo rules.

On cost, HELM notes that efficiency depends on both the model and the hardware ([HELM](https://ar5iv.labs.arxiv.org/html/2211.09110)). Hosted latency also mixes in network delay, queueing and rate-limit retries, and Modal-style servers add cold starts (Kev-4B: about 35 s) ([Kev README](https://github.com/jaredpalmer/kev)). The defensible protocol measures p50/p95 latency one request at a time on a warm run of about 50 items, with cold starts reported separately and cache hits excluded. It labels local numbers with the hardware, backend and quantization, and reports $ per 1,000 items from the providers' token counts. Tokens and parameters are the axes that do not depend on hardware. For one-pass models, count input tokens; their "output tokens" are near zero by construction. A Pareto plot (systems that no cheaper system beats on accuracy), drawn per cost axis with bootstrap error bars and log-scaled $ and latency, shows the trade-off directly. At n = 319, overlapping error bars mean two systems are not distinguishable.

## Thinking budgets and fine-tuning are the two costlier levers

**Thinking budgets** set how many hidden reasoning tokens a model spends before answering. More is not reliably better. Gema et al. found that longer reasoning *degraded* accuracy on tasks with distractors and spurious features, and that Claude models got more distracted by irrelevant information ([arXiv 2507.14417](https://arxiv.org/abs/2507.14417)). OpenAI notes that many workflows do fine at low effort ([OpenAI GPT-5 guide](https://developers.openai.com/api/docs/guides/gpt-5)). OpenJev adds an optional `think` budget for "multi-step problems" (512+ tokens recommended) but reports no measured gain. Input is billed twice and the thought counts as output ([OpenJev README](https://github.com/razorback16/openjev)). A clean ablation is OpenJev `think` 0 vs 512 on Q3/Q4, the counterfactual questions the docs flag. It would measure accuracy change, extra tokens and extra latency, with paired bootstrap intervals on the same items. Across providers, "minimal" settings are not equal amounts of thinking: Anthropic's manual budget starts at 1,024 tokens and newer models use adaptive effort ([Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)). Report the *actual* reasoning tokens used next to each setting name.

**Fine-tuning a small model** is feasible but requires building training data first. The public ASIMOV bucket holds only a `val` split for the text benchmark; the v1 "Injury train" set described in the v1 paper is not there ([GCS listing](https://storage.googleapis.com/storage/v1/b/gresearch/o?prefix=robotics/asimov)). The eval items were built from **NEISS 2023** injury narratives ([ASIMOV-2.0 paper](https://arxiv.org/html/2509.21651v2)). NEISS publishes annual files for about 20 years ([CPSC NEISS](https://www.cpsc.gov/Research--Statistics/NEISS-Injury-Data)), so narratives from 2019–2022 or 2024 cannot be the same cases. A teacher LLM can turn them into ASIMOV-style scenarios and answer the four questions, keeping its option probabilities as "soft labels". Before training, compare every synthetic scenario with all 319 eval prompts (text n-gram overlap and embedding similarity). Drop near-duplicates, using a threshold fixed and logged *before* looking at which eval items match. Balance the data by NEISS's own distribution, not the eval label distribution, because using the eval distribution would be tuning on eval. The ASIMOV v1 `asimov_injury_val` set (304 items) is also from NEISS 2023, so it needs the same dedup check ([features.json](https://storage.googleapis.com/gresearch/robotics/asimov_injury_val/0.1.0/features.json)).

Two training templates exist. Kev's recipe is a frozen base, a rank-16 LoRA and a pointer head trained with cross-entropy, about 1 hour on one H100 for 4B. Users report that fine-tuning from the *released* Kev adapter kept general accuracy (0.83) while reaching 0.88 on a new domain. Fine-tuning from the raw base collapsed to 0.33 ([Kev README](https://github.com/jaredpalmer/kev)). Laya is a 421M ModernBERT encoder whose fine-tuning notebook runs on two free T4 GPUs ([Laya card](https://huggingface.co/convaiinnovations/laya)). For training on rationales, models of 3B or less learn better from **short** explanations than from long chains of thought ([Li et al., arXiv 2502.12143](https://arxiv.org/abs/2502.12143)). Distilling step-by-step let a 770M model beat few-shot 540B PaLM on one benchmark ([arXiv 2305.02301](https://arxiv.org/abs/2305.02301)). On the 16 GB Mac, `mlx-lm` runs LoRA, and runs QLoRA automatically when given a quantized model. Its only published speed figure is about 250 tokens/s for a 7B model on a 32 GB M1 Max ([mlx-lm LORA.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)), so a 50-iteration test run should measure local speed first. Modal's $30/month free credit covers several 1-hour GPU runs ([Modal pricing](https://modal.com/pricing)). Ask before any paid run. Two caveats apply. The teacher's agreement with the human labels caps what the student can learn. Any prompt or checkpoint chosen by looking at eval accuracy is selection on eval, so selection belongs on a synthetic dev split, with the 319 read once per final model.

## Conclusion

The evidence shifts where the risk lies. Cost is nearly solved: hosted decision models make a full ASIMOV pass cost less than a cent per hundred items, and cascades can be simulated without new calls. The open problem is validity. Every published accuracy figure comes from tasks unlike ASIMOV. The documented weaknesses (ordinal scales, counterfactual reasoning, first-option bias, silent truncation) map onto specific ASIMOV questions. And prompt wording alone has moved accuracy by tens of points in other work. That makes per-question results, wording spread and order-bias checks essential parts of any accuracy-per-cost claim, not extras.

The second implication is structural. ASIMOV's chained question design clashes with how every decision API works, because all of them evaluate questions independently. So "how should the task be decomposed?" is itself an experimental variable with a cost (extra calls) and a risk (errors propagating from Q1). Whichever way the team goes, two decisions need the owner before any run: how Q2–Q4 are scored when a model picks a different injury than the key, and whether cross-fitting calibration on eval labels counts as tuning on eval.
